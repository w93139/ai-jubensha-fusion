# 阶段 3C 后续：固定元数据装配与真实编译验收

历史节点状态（2026-09-05）：固定字段装配与规则诊断已实现，离线/浏览器/构建通过；当时真实任务被候选规则校验阻断。后续于 2026-09-06 完成[规则契约筛查与合成小样本真实闭环](PHASE_3_RULE_CONTRACT_REVIEW.md)，默认 Compiler v4 / Audit v3，最新结果以该记录为准。下文保留本节点的原始失败和测试证据；继续采用既有 FastAPI/Next.js/SQLAlchemy 基座，无新增依赖。

## 问题与目标

上轮两次真实 Compiler 分别被摘录引用和冻结元数据检查阻断。因当时未保存细项诊断，不能推断是哪条正文或哪个字段错误；已确定的工程问题是来源可选空值误拒绝（已离线修复）。当前模型还要重抄已有的版本、文件路径、SHA-256 和原件关联，这些值本来就由服务端确定。新设计从模型职责中移除这些固定字段，服务端将模型内容草稿装配成完整候选，再执行已有严格校验。

本轮目标：保持现有来源与正文校验、费用预占、取消/恢复及人审边界，完成模型草稿 → 服务端候选装配 → 来源核验/保存 → 模型 Audit 的小型真实链路验收。不处理全量商业本、最终发布、运行会话绑定或语音。

## 契约与实现

- 新模型输出 `compiler-draft/1.0`：`schema_version/status/content/blockers`；`content` 仅有 introduction、characters、initial_phase_id、phases、knowledge、evidence、truth、settlement。
- 草稿只允许 CANDIDATE（content 非空、blockers 为空）或 BLOCKED（content=null、blockers 非空）。字段严格校验，模型夹带包版本/来源表/审批字段一律拒绝，不静默删除。
- `schema_version=script-package/1.1`、script_key、title、content_version、player_count、sources 由冻结 context 深拷贝装配；模型仍用已授权 source_id 和定位声明正文依据。
- 装配后复用 `parse_compiler_output` 与确定性包/来源校验。不存在于所选文字的正文、未读图片引用、错误阶段/权限、缺失结算和不支持机制仍阻断。
- COMPILE 输入只包含 title、player_count、materials、notes 和服务端定位目录；不再发送固定包标识、内容版本、文件路径/哈希或原件关联。私有完整 context 仍绑定原任务输入哈希。
- 默认模型契约升级为 `authoring-model/1.1`，请求契约 `bailian-authoring-json/1.1`，新增 Compiler v3 Prompt；Audit 输出和 HTTP/前端 DTO 形状不改。失败后扩展既有诊断字段的规则代码白名单，详见下文。
- 持久账本兼容读取旧 1.0 的配对版本，不重写旧任务、收据或候选哈希。新 worker 不以新契约重发旧任务。无数据库 schema 变更。

4. 成功须同时满足：编译结构和来源通过；固定元数据由本地组装一致；两角色各自事实、开场公开证据、系统真相和结算归属正确；Audit 五维完整且无 blocker；数据库重读及账本一致。仅“模型说通过”不算完成。

无效模型正文不进入公开日志。失败诊断只记录固定代码/字段路径；真实全链如未通过必须如实保留待验状态。

## 失败后的限定离线改进

候选校验已经生成规则问题，但模型适配层只抛出总错误码，导致合法草稿中的阶段、角色和线索关系错误无法定位。本轮补齐这个已确认的可观测性缺口：把已知确定性错误转换为最多 10 条 `PACKAGE_*` 固定代码与字段位置，严格校验代码/路径配对及数组上界；不透传原文、ID、来源数组、错误 message 或未知字段。工作台为这些代码显示固定中文说明，旧正文/元数据诊断保持兼容。

该修改只增加失败收据的可诊断性，不放宽候选规则，不改变 v3 Prompt、模型请求、候选哈希或历史收据。历史真实失败不会被补填后来才新增的诊断。用离线失败响应验证账本与页面后结束本轮，不追加真实调用。
