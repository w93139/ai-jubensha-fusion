## 结论

可以选用，但当前不建议把整个文件夹合入项目，也不建议直接安装到游戏后端的虚拟环境。先完成 M3 用户验收与新增 ASR 的真实验收；出现多用户并发运营、多模型或集中管理需求时，再通过独立部署的 LiteLLM Proxy 做小范围验证，不新增阻塞 M3 的开发阶段。这里的多用户运营不表示游戏要改为五真人联机。

LiteLLM 可以理解为“模型调用的总机”：统一接入供应商、管理调用凭证、统计用量、限制请求量。它不能直接保证角色不泄密、推理正确或剧本审核准确。其 SDK 与 Proxy 的定位见[官方说明](https://docs.litellm.ai/)。

## 对本项目的价值

| 能力 | 当前情况与采用建议 |
| --- | --- |
| 统一管理模型供应商 | 项目已有豆包和千问适配；供应商增加后收益更明显。先保留每局固定渠道，不静默换模型。 |
| 汇总费用、耗时、错误 | 对运营排查有用；游戏自身的逐局预算账本仍是扣费控制依据，不能直接用网关统计替代。 |
| 限流和并发管理 | 玩家规模扩大时有价值；需验证超时和排队不会导致同一动作重复调用。 |
| 虚拟密钥和后台 | 可管理服务调用权限；不能替代玩家登录、角色材料权限或剧本审核后台。 |
| 多 Agent 管理 | 网关可登记和管理独立 A2A Agent 服务；当前五席角色逻辑不必拆成五个外部服务，也不必每角色申请供应商 Key。仍由游戏后端构造各角色输入。 |
| 自动重试、备用模型、缓存 | 现阶段角色互动不启用：重试可能重复收费，换模型改变本局绑定，共享缓存需另做隔离验证。 |

这些属于网关能力；具体配置、日志和预算选项见[官方配置说明](https://docs.litellm.ai/docs/proxy/config_settings)。

## 已核实的接入障碍

1. **当前依赖存在明确冲突。** 本地 LiteLLM `pyproject.toml` 声明版本为 `1.101.0`，要求 `openai>=2.20.0,<3.0.0`。本项目 `backend/uv.lock` 固定 OpenAI `1.93.1`；当前安装的 `langchain-openai` 要求 `openai>=1.86.0,<2.0.0`。保持现有版本时不能直接安装这份 SDK。独立运行 Proxy 可避免将这些升级强加到游戏后端。
2. **严格输出参数有静态兼容风险。** 本地 `litellm/llms/volcengine/chat/transformation.py` 的 `get_supported_openai_params()` 未列出 `response_format`，而项目 `backend/src/fusion/providers.py` 使用它传入严格 JSON Schema。LiteLLM 的不支持参数检查可能拒绝参数，或在启用 `drop_params` 时删除参数。不能用删除参数来“解决”兼容问题。这里只做了源码与 AST 检查，尚未运行验证具体路由。官方也要求逐模型确认 [JSON Schema 支持情况](https://docs.litellm.ai/docs/completion/json_mode)。
3. **具体模型目录需补充核验。** 本地 `model_prices_and_context_window.json` 没有当前两个完整型号 `doubao-seed-character-260628` 和 `qwen3.7-flash-2026-07-15`。这不等于不能调用，但不能据内置目录认定其价格、上下文及结构化输出能力准确。
4. **源码快照尚无可验证的发布标识。** 文件夹没有 Git 元数据；目录名不能证明它不稳定，也不能证明它是已核验发布版。实际采用时应另选经核验并固定版本的发行包或镜像。根目录 MIT 许可证与 `enterprise/LICENSE.md` 的企业目录条款不同，不能将全部功能都视为同一许可。
5. **现有服务不允许随意改调用地址。** `backend/src/fusion/providers.py` 有供应商、模型及地址白名单，角色请求还绑定参数和端点指纹。接入需要显式的新传输配置，不能仅把 `.env` 的地址替换成网关地址。
6. **有预算预占，不等于能替代本项目账本。** `litellm/proxy/spend_tracking/budget_reservation.py` 已实现请求前费用预占，不能概括为“只有事后统计”。但无法估价或估价不大于零时会跳过这项预占；`fail_closed_budget_enforcement` 不是默认开启，存储故障和剩余预算不足策略需单独测试。取消/断连路径通常按估算输入费用结算预占，与游戏对未知结果的保守处理不同；不能因此释放游戏原账本的未知费用。
7. **会话预算不能直接当整局预算。** `litellm/proxy/hooks/max_budget_per_session_limiter.py` 的默认 TTL 为 3600 秒，成功回调累计后约束后续调用；长局、跨小时及恢复时需专门验证。它与上项请求预占是不同机制，不应混为同一个完整保证。
8. **币种和缓存价格需要对账。** 本地 `litellm/cost_calculator.py` 以美元计算，本项目账本为人民币。必须明确换算和费率版本，不能把 ¥5 原样填成 $5；补充实际型号的输入、输出及缓存命中价格，同一调用的代理和业务记录不能重复算成本。[自定义价格配置](https://docs.litellm.ai/docs/proxy/custom_pricing)
9. **豆包专用 ASR 尚无开箱接入证据。** 所核对的源码/模型目录没有项目使用的 `volc.bigasr.auc_turbo`、`auc_turbo` 或 `openspeech.bytedance.com` 专用适配证据。通用转发仍需鉴权、音频、取消和时长计费适配验证；不能因支持某些语音接口就认定当前豆包识别可以直接迁移。

## 开源范围与运营成本

官方将统一网关、虚拟密钥、用户/团队、基础费用统计和预算列为 OSS 基础；项目、标签预算、每虚拟 Key 的分模型预算、软预算邮件与部分报表列在企业功能中。采用前按实际版本核对，不把全部控制能力视为免费；企业费用尚无本项目报价。[官方功能与价格说明](https://docs.litellm.ai/docs/enterprise)

独立 A2A 服务的内部模型调用需要经网关并转发 trace/agent 标识，才能完整归因；“登记了 Agent”不能证明其所有内部费用均已统计。[A2A 接入说明](https://docs.litellm.ai/docs/a2a)

建议先按游戏运行、后台准备/审核、开发测试划分调用凭证，以局/角色/动作元数据接入本项目记录。是否购买精细预算功能另行评估。LiteLLM 不直接降低供应商 Token 单价，会增加服务、数据库/缓存和维护开销；未完成实测前不承诺单局节省比例或固定月费。

## 建议接法与验收范围

链路：玩家页面 → 现有游戏后端（权限、规则、预算、输出校验）→ 可选独立 LiteLLM Proxy → 本局固定的供应商与模型。

接入点应沿当前 Fusion 的 `backend/src/fusion/providers.py` 供应商适配及现有模型调用/账本链核对，不绕过它改用旧通用服务入口；直连方式保留，旧会话不自动升级。先使用虚构材料和模拟上游验证：

- 严格 Schema、思考开关和输出上限到达上游时完全保留，不能静默删参。
- 单次游戏调用最多触发一次上游请求；显式禁用内部重试、跨供应商回退及响应缓存，并核对任何会额外生成请求的功能。
- 网关别名绑定固定上游模型和路由版本，保存可核对的实际目标信息，不能只靠可变别名冒充原有模型指纹。
- 成功、超时、断连和未知结果均保留原预算、用量及幂等语义；恢复游戏不重发未知请求。
- 验证并发临近预算、未知模型费率、存储不可用、跨小时及重启后的预算；按相同用量核对人民币账本与网关金额。
- 仅记录排障所需元数据，关闭私本、提示正文和完整回答的日志保存；逐项检查回调、遥测和网关持久日志配置。
- 网关故障时仍能读取已有游戏记录，并明确说明当前动作未完成。

上述离线验证通过后，才准备独立、受限的真实兼容验收；本评估没有创建或执行新的付费批次。
